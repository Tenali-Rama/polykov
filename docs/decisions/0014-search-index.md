# 0014 — Search index and fuzzy matching

- **Status**: accepted
- **Context**: Global search must find any live object by full text, fuzzily (prefix, substring, one typo), in under 100 ms on 100k objects, on a 2 vCPU VM (spec "Organization", §10).
- **Decision**: One FTS5 table `search` (migration 6) with the **trigram** tokenizer (case-insensitive), one row per live object keyed by its id, columns `title`, `tags` (space-joined), `props` (every string value in `properties`, nested ones included) and `comments` (bodies, space-joined). Triggers on `objects` (insert; update of title/properties/deleted_at; delete), `object_tags` and `comments` rebuild the touched object's row from the `search_source` view, which yields nothing for trashed objects. Matching is two-step: query words are the letter/digit runs of `q` (so FTS syntax never reaches FTS5); the index narrows candidates with, per word of 3+ chars, `"word"`, OR'd with either half of it for a 6+ char word that occurs exactly nowhere (one typo always leaves a half intact; expanding common words made every row a candidate and broke the budget). Then `search::fuzzy` checks every word in Rust: exact substring, else, for an expanded word, edit distance ≤ 1. Score = Σ per word of the best column weight (title 4, tags 2, props 1, comments 1) × quality (whole word 4, prefix 3, substring 2, typo 1); ties newest id first. A query with no word of 3+ chars (the palette's first keystrokes) can't use the index, so it matches titles only, each word at a word start (whole word or prefix), scored the same way: one pass over `objects.title` with an allocation-free check (`fuzzy::word_start`), ~30 ms CPU on 100k, instead of folding and scoring four columns of every row (~125 ms).
- **Consequences**: Short-only queries don't see tags, properties or comments, and `ee` doesn't find `meeting`; mixed queries still check short words anywhere in the FTS candidates. Words of 3–5 chars, and words with an exact match somewhere, don't tolerate typos. New searchable text (note bodies, M4) is a new column or a change to `search_source` plus triggers, in a new migration. Keep the Rust check a filter over the FTS candidates: the FTS expression must stay a superset of what `fuzzy::find` accepts. `fuzzy::fold` keeps only the first char of a multi-char lowercase mapping, while trigram uses SQLite's own folding, so on rare non-ASCII letters the two can disagree and a match may be missed.
